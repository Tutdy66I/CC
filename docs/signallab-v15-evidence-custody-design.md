## 威胁模型和信任边界

保护目标包括原始字节完整性、发布授权、版本新鲜度、恢复可用性和审查可重复性。假设攻击者可能控制构建机、GitHub 帐户、任一备份方、恢复目录或网络入口，也可能选择性隐藏最新记录。故障还包括介质损坏、时间不可靠、软件供应链被替换、密钥遗失与人员离场。签名只说明获授权密钥批准了特定字节与上下文。签名前输入验证、运行时身份和可复现性各有独立验收门槛。

如攻击者同时控制 ZIP、manifest、anchor 和调用方接受的预期摘要，可以为替换件生成自洽的整套哈希。建立真实性需要恢复方事先拥有来自独立渠道的授权公钥、验证策略与可信检查点。仅盗取存储帐户时，签名和独立的版本检查点可拒绝替换及回滚，但存储方仍可拒绝提供数据。发布者被攻破后，单签方案可能批准虚假证据。双角色复核能降低单点风险，但无法挽救角色共谋、两把密钥均失守，或验证根和检查点同时被替换。验证根无法独立找回时，恢复验收应明确停在“字节可读，来源待证”。

## 可信锚点候选

两条候选共享一个待验证的签名声明。以固定域前缀和版本绑定规范 UTF-8 JSON 字节，采用明确的规范化规则，例如 [RFC 8785](https://www.rfc-editor.org/rfc/rfc8785)。声明至少含项目与证据类别、固定合成标记、归档 ID、序号、上一声明的摘要、ZIP／外部 manifest／anchor 的 SHA-256 和长度、源提交与依赖清单摘要、验证策略 ID、签名角色与密钥 ID。分离签名及时间凭证，避免自引用。摘要针对原始字节，签名针对规范声明。验证器拒绝未知版本、重复字段、歧义编码、未批准的算法及角色；以已信任的策略决定算法，不能由待验对象放宽门槛。发布者自报时间仅作记录。时间戳证实特定摘要在时间界限前已存在，授权、顺序及“这是最新版”都需单独验证。

| 维度             | A．离线双角色批准与独立见证                                                                                                                                                                | B．隔离签名服务与外部时间戳                                                                                                                                                            |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 身份及绑定       | 发布者和独立审查方分别用角色专属签名批准同一声明，两签均须有效。例如使用 [RFC 8032 Ed25519](https://www.rfc-editor.org/rfc/rfc8032)。审查方独立核对来源、产物和上一序号后再签。            | 签名服务只允许受批准的发布角色按签名策略提交声明，验收验证签名、授权策略和服务返回的审批记录。CI 仅提交候选，无法自行批准或导出密钥。                                                  |
| 生成与保管       | 将来在隔离设备或各自硬件令牌内生成并保管密钥。发布、复核及备份管理使用不同身份，CI 无私钥。离线根的恢复材料分人保管，见证者另存签名索引。                                                  | 将来由隔离签名服务内部生成不可导出密钥，并独立管理策略和操作审计。权限配置由专门管理员负责，签名调用要求人工或独立审批。服务运营方与备份运营方分辖。                                   |
| 轮换、吊销和失效 | 用预先分发的离线根签出新公钥、角色及生效序号。独立见证旧／新序号交接。保存历史密钥和撤销资料。失陷时停止接受新增签名，隔离可疑时间窗，只有能独立证明在可信截止点前获批的记录才可重新评估。 | 归档公钥版本、授权政策及历史撤销凭证，冻结失陷的签名角色，独立发布截止点和新授权。时间戳机构密钥变化同样需要保存历史链、政策和撤销材料。停用密钥不等于销毁历史验证能力。               |
| 时间和顺序       | 序号与前序摘要构成链，独立方保存并签署单调检查点。由持有可信版本的见证者发现分叉与回滚。顺序不提供可靠 UTC，也不证明没有遗漏最新事件。                                                     | 可对带签名的原始声明封装建立 [RFC 3161 时间戳](https://www.rfc-editor.org/rfc/rfc3161)。另由独立方保存序号检查点，并跨渠道核对版本；时间戳本身不能防止回滚或隐匿。                     |
| 验证根及失陷影响 | 审查方在接触证据包之前，通过线下交换与第二渠道核对根指纹，并独立保存根、角色清单、撤销表与最新检查点。任一签名方失陷会中断发布，双签均失陷时可能伪造，见证过的旧记录仍可供调查。           | 审查方预先固定签名与时间戳验证根、允许政策和独立检查点，而非采用归档内附带的根。签名服务或发布授权被攻破可产生看似正常的签名，即使另有时间戳。时间戳服务失效会阻塞需要该凭证的新发布。 |
| 成本及可运维性   | 基础设备及服务成本较低。人工在场、轮换和灾难交接成本较高，适合小批量审查。                                                                                                                 | 发布规模较大时更便捷。需要服务、运营人员、长期验证材料和供应方迁移预案，成本和信任面较大。                                                                                             |

**建议先评估 A**。首轮规模允许用双角色及独立见证来测试信任边界。若后续确实需要可独立验证的 UTC 时间，再评估 B 中的时间服务与长期验证材料。此轮未选择具体服务商、生产算法配置、密钥持有人或凭据。

## 独立故障域及最低门槛

候选最低拓扑为发布／构建域 P、两个可独立恢复的存储域 S1／S2、独立持有验证根与检查点的审查域 W。S1 和 S2 各持完整证据和恢复说明。P 授权只写入新版本，无法覆盖旧对象、删除旧版本、解除保留或修改 W。备份账户、管理员／恢复身份、根凭据、管理平台、设备介质及物理位置应隔离。共享同一个有全权的管理员、身份提供方恢复链、管理员凭据、存储后端或单一可销毁地点时，必须记录共同故障域，不计作两个独立副本。锚点保管和副本保管是不同控制。

| 候选                        | 典型构成                                                                                                                     | 成本、复杂度及剩余风险                                                                                                                 |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| X．离线异地介质             | 两组独立设备或介质，分地点和保管人，各自保留不可覆写版本或写后断开。由双人审批销毁与迁移。                                   | 订阅成本低，人工取送、盘点、设备更新和恢复时间较高。存在遗失、介质老化、离线副本滞后与格式过时。                                       |
| Y．独立不可变存储加离线副本 | 一个具备不可变保留与独立管理员的对象存储，第二副本写入另一控制面下的离线介质。上传权限和保留管理员分离，保留通道设独立日志。 | 在线取回较快，需管理存储、下载、保留配置与退出成本。仍面临供应商服务停摆、错误配置、区域相关性及身份供应链风险，离线副本需能独立工作。 |

候选运维门槛为备份每一个获准发布版本，保留不可变历史和替代／撤销记录。明确保留期限、终止条件与销毁批准人后才准入；可行性测算可先用 12 个月作为容量假设，并非实际承诺。新版本不替换旧版本，存储和签名格式迁移应链接原始摘要并保全原件。每月核查可读性、对象清单、全部摘要和检查点。每季度及任何密钥、介质或工具链重大变更后做一次隔离恢复抽查。将“已备份”限制为有两份逐字节核验过的写入回执，候选恢复目标为保住最近一个已确认版本并在一个工作日内取回，实际 RPO／RTO 待演练测量。故障时冻结删除，隔离损坏副本，记录完整告警及处置，从已认证副本迁移并重建冗余后恢复发布。供应商退出或供应链异常时，应能使用第二域、离线工具与已核验恢复介质。发生冲突时保留各版本、日志与对象身份。

独立日志至少包括操作者角色、发布序号、对象与策略摘要、写入回执、完整性巡检、读取／恢复、访问权和保留配置变更、销毁审批及结果。日志应由独立身份管理，保留只追加的检查点并在 W 保存副本。单一服务的运维日志无法单独证明其管理员行为。档案候选至少保存原始证据与输出、摘要清单及签名声明、来源和构建证明、独立检查点／时间凭证、历史验证根与撤销记录、只读验证工具、恢复说明和回执。能支持重执行的依赖包与原始证据分组保存，分别核验其身份。

## 跨环境恢复验收矩阵

文件恢复和科学复现分别签发结果。**文件恢复**要求外部验证根、签名授权、预期序号、原始字节和清单都一致，复核人能从独立位置重算摘要。**科学复现**还要求经批准的源码、可重建或可重放的 Node／V8／Python 与原生依赖、平台及浮点语义、固定公开输入和预注册的比较判据。先保存原始字节，再在隔离环境重新执行。按原始包和新运行分别记录摘要、输出分类与差异，不能替换原件或将“不可复现／未验证”写为通过。服务不可用时，允许保全候选字节，但不授予完整验收状态。

| 条件                           | 所需证据与验证方法                                                                                                       | 失败关闭、可信结果及剩余限制                                                                                                                           |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 原始环境完全不可用             | 从 W 预置根与检查点，从 S1 或 S2 取回包、验证工具和恢复说明。独立人员在隔离环境生成恢复回执。                            | 缺根、缺授权、缺对象或摘要不匹配则不得验收。全量逐字节核对通过后仅授予文件恢复；跨机可执行性另验。                                                     |
| Actions 工件已过期             | 禁用原始工作区与 CI 入口，将证据版本固定到独立回执和检查点，核算全部文件。                                               | 若需要登录 GitHub 获取缺失原件、检查点或验证器，则独立恢复失败。临时链接不能补足长期保留证据。                                                         |
| 部分损坏或截断                 | 保留损坏件与日志，检查 ZIP、manifest、全长及逐成员摘要。从另一域重新检索同一经认证版本。                                 | 损坏件隔离，拒绝静默修补。对第二份原件重新完成全量校验，可出具单独恢复回执。两域均损坏时无法保证取回。                                                 |

## 下一阶段决定

**Go，限另行批准的公开合成实验。No-Go，针对真实证据保管、独立恢复验收和 `05-evidence` 冻结。** 首轮优先使用现有固定合成样本、公开标准测试向量或标明无生产效力的模拟信任材料，保留 PR #33 的原始三件对象。候选实验应具备以下可验收结果。

1. 通过独立渠道向执行人预先交付合成验证根与检查点，分别验证规范声明、正反向签名向量、角色错误、锚点替换、已签旧版本回滚和模拟撤销。只有使用同包提供的替换根才能通过的输入应明确列为不可信。
2. 在原始工作区和 CI 不可用的演练条件下，让另一操作者在第二台隔离机器从预先布置的合成副本重算原始字节摘要。记录读写身份、故障域、回执、截止点与恢复用时。若只能用同机或共享管理域，应明确限制实验结论。
3. 对符号链接、并发替换、截断、中断恢复及副本分叉分别记录拒绝点。用一个版本不同的恢复环境演示“文件通过、数值未验证”。只有验证了允许环境的依赖闭包与事先约定的判据，才评估固定合成结果的数值重放。

独立复审应明确确认角色隔离、可信根发放与撤销流程、防回滚策略、两域留存及恢复权限、可审计的恢复回执和环境等价边界。缺任一项时继续保留相应未验证状态。本轮采用文档交付，未实现协议、创建密钥或凭据、上传证据或部署存储。
